# DSH · WSL Desktop

简体中文 | [English](<README.en.md>)

Windows 原生 **Tauri 2 + WebView2** 桌面应用。DSH、Node、会话与项目继续运行在 WSL；应用负责服务控制、现有 Web 工作区，以及可选的桌宠与轻量对话入口。

## 使用方法

> **这是已有 WSL Harness 环境的启动器，不是 Harness 安装器。** 首次引导可部署随包内置的 MIT 自有 Python 管理器 1.0.0 并生成服务配置，无需另找私有脚本；不会安装 WSL 或软件、克隆项目、安装依赖、运行构建或配置 API Key。新克隆的 Harness 必须先在 WSL 中手动准备完成。

### 1. 准备运行环境

- Windows x64，并安装 WebView2 Runtime；从 [GitHub Releases](https://github.com/elves-ai/dsh-wsl-desktop/releases) 下载并运行 NSIS 安装包，或使用独立可执行文件。详见[下载与安装说明](<DOWNLOADS.md>)。
- 已安装且可用的 WSL 发行版和 Linux 用户；该用户可执行 `/usr/bin/python3`（Python >= 3.9）和 `ss` 命令（通常由 iproute2 提供）。内置管理器还要求可用的 Linux `pidfd`（建议使用 WSL 2）；首次部署前会只读检查，不支持时不会保存配置或回退为不安全的 PID 停止。
- WSL 中已有 DeepSeek Harness **源码项目**，以及满足该版本要求的 Node.js 和 pnpm；以 Harness 项目清单中的 `engines.node`、`packageManager` 及上游开发文档为准。
- Harness 已安装依赖并完成该版本要求的完整构建；Node 必须已存在。首次引导仅探测并选择现有 Node，不负责安装。已有旧启动器配置的用户继续自动导入并复用旧管理脚本和数据，见[配置](<#配置>)。

本启动器使用源码入口启动，不能把 npm 全局安装目录或普通工作项目目录当作 Harness 目录。

### 2. 如果 Harness 是新克隆的项目

在 **WSL 终端**中进入 Harness 项目根目录执行（不是本 Windows 启动器项目）：

~~~bash
# 替换为你在 WSL 中的 Harness 源码目录
cd /home/your-user/deepseek-harness
pnpm install
pnpm run build
~~~

还未克隆时，先按 [Harness 上游源码运行说明](https://github.com/deepseek-ai/deepseek-harness#run-from-source) 获取项目。Node、pnpm 版本及原生编译工具等要求随 Harness 版本变化，按所克隆版本的文档准备；命令失败时先解决安装或构建报错，再回到启动器。

`pnpm run build` 用于准备 Harness 运行所需的构建产物，包括 Web/客户端资源及相应运行时产物。后端能通过 tsx 运行源码，**不代表新克隆项目可以跳过构建**；仅执行 `build:web` 也不保证其他运行产物已经就绪。这里不需要生成 Windows 安装包，也不需要构建本启动器。已有完整环境可以跳过这一步；更新 Harness 源码后，应按该版本要求重新安装依赖、构建。

### 3. 首次引导或使用已有配置

仅当 **Windows 应用配置不存在，且旧启动器配置也不存在** 时显示首次引导。已有旧配置照旧导入，原文件不变；已有但无效的 Windows 或旧配置会报告错误，不会被引导自动覆盖。

1. 选择已有的 WSL 发行版、Linux 用户，通过 Windows 原生 `IFileOpenDialog` 系统弹窗选择 **WSL 内的 Harness 源码根目录**。引导自动探测该用户 nvm 中的最高已安装版本或系统 Node，也可通过同一系统弹窗选择已有 Node 可执行文件；探测到的版本仍须满足 Harness 要求。repo、Node 路径只读、不手输，不使用自制浏览器；选择结果转为当前 WSL 发行版路径，拒绝 Windows host 和其他发行版。
2. 端口默认 `3080`，可在高级选项修改。只选择或检查环境不会部署管理器或生成两端配置。
3. 点击“完成配置并启动”后，先复用只读环境检查；通过后才部署内置管理器、生成 Linux 与 Windows 配置，并进入现有服务启动流程。缺少前置条件时按提示手动处理后重试，不会代装软件或执行构建。部署路径、重试与发布顺序见[配置](<#配置>)。

**已有配置的日常目录调整：**

1. 启动 Windows 应用。已有配置通过环境检查后直接打开 DSH，无需点击继续。
2. 要更换或补充项目目录，点击左上角 Logo 旁独立的“设置”齿轮图标，在当前窗口的设置页中选择“环境与目录”。已有受管理服务运行时，先通过托盘右键菜单停止服务；若服务正在启动，先等待就绪。外部服务需在原启动终端中自行处理。
3. 通过 Windows 原生 `IFileOpenDialog` 系统弹窗选择 **WSL 内的 Harness 项目根目录**；只读字段显示返回的 WSL 绝对路径，例如：
   ~~~text
   /home/your-user/deepseek-harness
   ~~~
   不接受 Windows host 或其他 WSL 发行版路径；不要选择普通工作项目目录或 Harness 的子目录。系统弹窗中的当前发行版 UNC 路径会转换为 WSL 路径，不需手输。
4. 点击“保存并重新检测”。只更新已有 Linux 服务配置的 `repository` 字段，保留 Node、端口、数据目录等其他配置；不会安装依赖或运行构建。目录验证通过不代表依赖与构建产物都已就绪。
5. 检查失败时按提示手动处理，然后点击“重新检测”；无需重开应用。检查通过后自动启动或连接服务并打开 DSH。

这里选择的是 **Harness 程序所在目录**，不是让 AI 编辑的业务项目目录；业务项目应在进入 DSH 后选择。

### 4. 选定目录后，实际如何启动

~~~text
保存 repository → 检查运行环境 → 探测已有服务
  ├─ 已就绪：复用已有服务
  └─ 未启动：wsl.exe → 配置的 Python 管理脚本 → Node 启动 Harness
→ 等待服务就绪并确认 Windows 可访问 → 在 WebView 中打开 DSH
~~~

环境检查包括项目入口、Node 版本、已安装的 `tsx/esm` 依赖入口，以及 Web 页面和其引用的本地构建资源。以当前兼容的管理脚本为例，启动命令相当于在所选 Harness 根目录执行：

~~~bash
# 使用 Linux 服务配置中指定的 Node；端口以配置为准
node --import tsx/esm apps/cli/src/bin.ts web \
  --no-open --host 127.0.0.1 --port 3080
~~~

**启动阶段不会执行 `pnpm install` 或 `pnpm run build`。** 后端使用源码入口，Web 页面使用已生成的构建资源。检查未通过就不会进入服务启动阶段；如管理脚本启动后仍失败，需查看服务日志，不能把“检查通过”当作所有运行时功能都已验证。

### 5. 日常使用与退出

- 启动/停止/重启等服务操作仅位于托盘右键菜单；停止和重启需要确认。
- 关闭工作窗口只隐藏到托盘，后台任务继续；再次打开应用会唤起原窗口。
- 退出操作也仅位于托盘右键菜单：“仅退出启动器”保留 WSL 服务；“停止服务并退出”会先确认受管理服务已停止，再退出。
- 左上角 Logo 仅作展示，旁边独立的“设置”齿轮图标直接在当前主窗口内打开设置页，不弹出下拉菜单。设置页侧栏包含“环境与目录”“系统通知”“电源管理”“桌面宠物”“软件更新”“诊断日志”六个分类；查看日志请在侧栏选择“诊断日志”。托盘的诊断日志、检查更新、服务控制和退出入口保持不变。点击左上角“返回”恢复进入设置前的工作区或初始化页；原生 DSH WebView 保持存活，返回时不会重载。每个窗口的设置表单在切换分类、返回及重新打开设置时保留未保存输入。Windows 启动器更新不会更新 WSL 中的 Harness。

### 常见问题

| 现象 | 处理方式 |
| --- | --- |
| 新克隆的项目提示缺少依赖 | 在 WSL 的 Harness 根目录执行 `pnpm install`，成功后构建并重新检测；启动器不会代装。 |
| Web 构建产物缺失、不完整或不可读 | 在同一 Harness 根目录执行 `pnpm run build`，确认构建成功、资源可读后重新检测。 |
| 管理脚本或 Linux 配置缺失 | 全新环境由首次引导部署内置管理器并生成配置；已有配置则核对其路径并手动修复，不会被引导自动覆盖。日常“保存并重新检测”仅改项目目录。 |
| Node 不可执行或版本不兼容 | 首次引导可通过原生系统弹窗选择已有 Node；已有环境检查 Linux 服务配置中的绝对路径和项目版本要求。nvm 更新后旧路径可能失效，启动器不读取交互 shell 初始化。 |
| 目录无效或无法保存 | 使用有效的 Harness 源码根目录 WSL 绝对路径；确认已有 Linux 配置有效、服务已停止且配置端口空闲。 |
| 端口不一致、被其他程序占用或无法认证外部服务 | 对齐 Windows/Linux 配置端口，确认占用进程归属；外部手动启动服务应使用原终端认证链接或自行管理，不会被自动强停。 |
| 服务启动失败或等待超时 | 查看设置中的诊断日志及原 Python 管理器的服务日志；超时不表示服务已经停止，稍后重新检测，避免重复手动启动。 |
| 托管服务无法取得网页认证链接 | 网页认证与服务归属分别校验；可通过托盘右键菜单“停止服务…”正常停止已验证实例，再重新打开 DSH。不会因认证链接缺失把托管实例当成外部服务，也不会自动重启。 |
| 初始化或连接等待中需要退出 | 使用托盘右键菜单“仅退出启动器（保留服务）”，不必等待检测完成；关闭按钮仅隐藏到托盘。更新安装期间仍需先完成或取消安装。 |

## 功能

- 无新旧配置时提供首次引导，部署内置管理器并生成两端配置；已有旧配置自动导入，继续复用原管理器和数据。
- 自动检查/启动服务，确认 Windows 可访问后在 WebView 中打开 DSH。
- 单实例、单工作窗口，重复打开唤起原窗口。
- 启动进度、托盘、启动/停止/重启与脱敏操作日志。
- 启动器和 DSH 工作窗口使用单行自定义标题栏：左上角仅作展示的 Logo、独立的“设置”齿轮图标、软件标题和窗口按钮同一行，原“文件 / 设置 / 帮助”顶层菜单已移除。点击齿轮直接打开当前窗口的设置页，不弹出下拉菜单；诊断日志从设置页侧栏进入；托盘菜单保持不变，服务控制和退出操作只在托盘右键菜单中提供。空白区可拖动、双击最大化或还原，关闭按钮仍隐藏到托盘。
- 普通页面（桌宠除外）的右键菜单只保留“刷新”和“打开控制台”；控制台为当前页面的 WebView2 开发者工具（包含 Console、Elements、Network），不是终端或启动器诊断日志。桌宠使用下述专属操作菜单，托盘菜单不受影响。
- 关窗隐藏到托盘，不停止任务；“仅退出启动器”保留服务。
- 可选 Windows 原生系统通知：后台本轮正常结束／失败提醒、持久化开关与测试通知；默认关闭。
- 任务期间自动防休眠，默认开启；任一会话或子代理运行时保持系统唤醒，全部结束后释放，允许屏幕正常熄灭。可在“设置 → 电源管理”关闭并查看当前状态。
- “停止服务并退出”先确认停止成功再退出；危险操作原生确认框默认选中“否”。
- 启动时静默检查 GitHub 正式版本，不打断初始化、不自动弹窗；点击设置图标旁的“软件更新”图标直接进入更新页。有新版本时图标右上角显示红色小点，打开页面不会清除提醒；确认已是最新版后不再显示。手动确认后才下载、验签、安装，仅更新 Windows 启动器。详见[更新与密钥配置](<UPDATES.md>)。

不安装/升级 DSH，不修改原启动器，不迁移 Edge 登录数据，不接管整个 WSL，不自动强杀进程。

### 桌面助手（开发版）

“设置 → 桌面宠物 → 对话工作目录”只读显示当前绑定的 WSL Workspace 路径和发行版，支持“初始化宠物目录”、刷新与“打开目录查看”。初始化会准备固定目录、注册或复用 DSH 项目并连接会话，已有目录内容与历史不会清空，也不会发送消息或调用付费模型。目录未初始化或已丢失时，宠物气泡提供“去设置初始化”，不再误导为重新连接。宠物工作目录固定为 `~/.dsh-wsl-desktop/assistant`，不能在设置或对话面板中修改。真实对话历史仍由 DSH 保存，工作目录不是 DSH 消息存储位置。查看不会创建目录、启动聊天或调用付费模型；Windows 访问 WSL 目录可能唤醒对应发行版。未绑定、目录缺失／不可访问或当前后端身份已变化时禁止打开并提示原因；打开前重新核验绑定与后端身份，不接受前端传入路径。

待 Windows 实机验收：初次加载、刷新和重新进入设置后路径更新；中文／空格路径能在资源管理器打开；未绑定、目录移除、WSL 不可访问和切换发行版／用户／服务地址时均不打开错误目录，且不创建目录或对话。Linux 单测与 Windows 交叉检查不替代此验收。

点击标题栏软件更新图标旁的鱼形宠物图标，显示或隐藏鲸鱼娘；图标会同步实际显隐状态，也可以从托盘右键选择“桌面助手…”打开。开启显示桌宠时自动初始化固定的独立 WSL 工作目录 `~/.dsh-wsl-desktop/assistant`（只读、不可修改），注册或复用 DSH 项目并连接会话，不启动/停止 WSL 服务；服务未就绪时等待连接，失败可到宠物设置手动重试。不会指向 Harness 源码目录，也不会另配模型或另存聊天记录。旧自定义绑定会停用，保留原记录；再次开启宠物或在设置初始化后使用默认目录；旧目录、Workspace/Session 及其历史不搬移、不删除。默认目录的有效会话绑定仍会恢复；是否启动时显示桌宠由“设置 → 桌面宠物 → 启动时显示”决定，默认关闭。

“设置 → 桌面宠物”提供当前显示、启动时显示、允许漫游、允许弹弓和气泡通知五个选项；后四项保存在本机，关闭漫游仍可手动拖拽、抛掷和点播动作。弹弓默认开启，关闭即时生效，快速连按再拖不再蓄力弹射，不影响普通拖拽和甩抛。右键打开约 172px 宽的紧凑菜单，包含聊聊、打开 DSH、播放动作、允许弹弓、窗口置顶、宠物设置和隐藏；弹弓开关与设置页同步并自动保存。支持 X、点击外部、Esc、再次右键关闭，执行操作后自动收起。底部常驻操作栏与声明条、头顶状态标签已移除，作者链接和素材许可收进菜单；对话面板保留状态提示。置顶仅影响桌宠，本次运行内隐藏再显示保留，重启默认开启。

点击桌宠展开面板，可流式聊天、停止当前运行、新建/切换项目内对话，或“在 DSH 打开”同一会话。待答问题、计划评审和权限请求可在交互气泡或完整 DSH 工作区处理。停止不等于清空待处理队列，隐藏窗口不停止任务。面板不再提供“项目”、更换目录或初始化入口；需要初始化时直接引导到宠物设置，旧目录及对话历史不搬移、不删除。

桌宠直接复用 [dsh-pet](<https://github.com/PC2005-cloud/dsh-pet>) 的 106 个 VP9-alpha 动画、动作配置、随机选择、点击 Q 弹与甩抛/弹弓物理核心；窗口适配仍由 Tauri 完成，不引入 Electron。普通拖动直接跟随鼠标，采用目标约 60Hz 的串行调度，每帧一次原生 IPC 完成采样与移动，不积压过期帧；快速连按再拖的弹弓仍有弹性。屏幕工作区缓存 350ms，DPI、尺寸或当前工作区变化时提前刷新，目标与实际窗口位置相同时跳过重复定位。实际帧率和 CPU/GPU 收益仍需 Windows 实测。左右边界按角色而非透明留白计算，支持拖至边缘，**没有贴边自动收起或靠近自动展开**。

支持随机动作、转向、工作状态联动和漫游/固定。当前面板加载最近 100 组消息及后续实时事件，更早记录仍保存在 DSH，可在完整工作区查看。语音输入、自动读屏和换装不在本版范围。详见[实现与验收说明](<ASSISTANT.md>)；Windows 原生运行与真实模型对话尚需实机联调，不将浏览器预览或交叉类型检查视为发布验收。

### 任务期间防休眠

“设置 → 电源管理”中的“任务期间防休眠”默认开启，设置独立保存在应用配置目录的 power.json 中，不受系统通知开关影响。启动器登录本机 DSH 后约每 3 秒只读检查会话运行状态；多个会话或子代理中只要有一个仍在运行，就保持 Windows 系统防休眠请求。任务结束、失败或取消后，下一次检查发现全部不再运行即释放；等待用户回答时若 Agent 仍标记为运行，也继续保护。这里依据当前运行状态，不把长任务目标尚未完成等同于一直运行。

关闭工作窗口隐藏到托盘不影响保护。停用开关、服务离开就绪状态或退出启动器会释放请求；“仅退出启动器”虽然保留 WSL 服务，但退出后不再防休眠。临时查询失败时，仅对已经观察到的运行任务保留短暂保护，距最后有效运行状态约 30 秒后释放并继续重试，避免断线后无限保持唤醒。状态与错误可在电源管理页查看。

只调用 Windows 临时系统防休眠接口，不修改电源计划、不保持屏幕常亮，也不阻止用户手动睡眠、合盖、关机或系统强制休眠。不包含任务结束后自动关机功能。

## 架构与安全

~~~text
可信本地控制页 + 原生托盘 → Tauri Rust → wsl.exe → 内置或原有 Python 管理器 → WSL DSH
                                                                        ↑
                                                 无原生 IPC 的 DSH WebView
~~~

无配置时初始化窗口提供首次引导；配置就绪后负责启动进度与异常恢复；环境就绪后自动隐藏，进入 DSH 工作窗口。“环境与目录”“系统通知”“电源管理”“桌面宠物”“软件更新”“诊断日志”集中在当前主窗口内的设置页，不再打开独立原生设置窗口。左上角“返回”恢复原工作区或初始化页；原生 DSH WebView 始终保留，返回不会重载。设置表单按窗口保留，切换分类、返回及重新打开设置均不会丢失未保存输入。每个窗口的标题栏是单独的可信本地 WebView，与内容区隔离。服务、通知、电源管理和更新命令只授予初始化与设置内容 WebView；标题栏只能打开固定的设置/更新页面、读取更新提醒和宠物显隐的最小状态、切换桌宠显隐及操作自身窗口；不能检查、下载或安装更新。Rust 校验视图标签、父窗口、本地来源及页面路径和参数；远程 DSH 内容没有原生权限，也不注入标题栏脚本。

启动 URL 必须严格匹配配置的回环地址/端口。token 仅在内存中传给 WebView，不发送给控制页或写入操作日志。WSL 请求使用参数数组，不经过 shell，响应大小和等待时间有上限。外链只允许无启动 token、无用户信息的 HTTP(S) 地址。

配置的管理器负责去重、就绪检测、身份校验、SIGTERM 与等待退出。[安全停止适配器](<src-tauri/helpers/guarded_stop.py>)在原管理器持有操作锁时额外核对预期 PID、管理锁或原启动子进程的日志身份，以及进程启动时间，防止误停外部进程。适配器内嵌在应用中，经 Python 的 -c 参数执行，不覆盖旧脚本。只读状态探测使用同一身份依据，独立返回托管归属和网页认证结果；已验证的启动中实例或认证链接不可用的实例仍能正常停止。

“由启动器管理”包括同一已配置 Python 管理器托管的服务（含旧环境），并非仅本次桌面进程创建的实例。若管理进程已退出，但其分离的 DSH 子进程仍存活，不再仅因管理锁释放就判为外部：只有启动记录的 PID / 启动时间、当前用户 / 项目 / 命令行、监听端口，以及标准输出和错误输出指向的原日志 inode 全部吻合，才恢复托管识别、从该日志恢复认证并允许确认后停止。记录缺失、PID 被复用、日志替换或任一校验失败时，不接管或停止实例。外部手动启动的服务只尝试连接，不自动停止；新 WebView 无认证信息时明确报错。

[独立启动适配器](<src-tauri/helpers/detached_run.py>)使用参数数组，在 Linux 内创建独立会话并让管理器继承忽略 SIGHUP，避免仅依靠 Windows 的分离进程标志。适配器退出后仍由正常探测确认就绪；不覆盖旧管理脚本、不安装服务、不自动重启失败实例。

## 配置

配置选择顺序：使用已有 Windows 应用配置；不存在时导入旧 Windows 启动器配置（位置见下方），旧文件不变；两者都不存在时才进入首次引导。已有无效配置不会自动覆盖。旧环境的 Harness 目录、Node 路径和 DSH_HOME 仍按原管理器与 Linux 配置处理，旧脚本和数据不会自动替换或迁移。

~~~text
应用配置：%APPDATA%\io.local.dsh-wsl-desktop\config.json
操作日志：%APPDATA%\io.local.dsh-wsl-desktop\launcher.log
WebView 数据：%LOCALAPPDATA%\io.local.dsh-wsl-desktop\webview
旧配置来源：%LOCALAPPDATA%\DeepSeekHarnessLauncher\config.json
~~~

### 首次引导生成的配置

WSL 侧由本项目新建的数据统一放在家目录隐藏文件夹 `~/.dsh-wsl-desktop/`。桌宠工作目录固定为 `assistant/`，只读且不可修改，不另存聊天记录；旧自定义目录及历史不搬移、不删除。本地语音由分步安装流程管理同一根目录下的模型、默认 Python、运行依赖与原生构建；不提供目录选择，也不执行旧外部 Python。打开设置仅读取状态，显式安装才联网准备资源，检测成功后自动保存；不加载模型、开启自动朗读或修改系统驱动。详见[语音目录说明](<QWEN_SPEECH.md#默认数据目录>)。Windows 配置仍保留在上面的原生用户配置目录；已有 Linux 配置、外部环境、Harness 仓库和 DSH_HOME 不会自动迁移。

MIT 自有 Python 管理器 **1.0.0** 通过 Rust `include_str!` 内置随包提供，版本与桌面应用配套，不会远程下载“最新版”。点击“完成配置并启动”并通过部署前只读检查后，在所选 Linux 用户下使用以下位置：

~~~text
管理器：~/.dsh-wsl-desktop/manager-1.0.0.py
Linux 配置：~/.dsh-wsl-desktop/profiles/<profile-id>/config.json
状态/日志：~/.dsh-wsl-desktop/state/<profile-id>
~~~

`profile-id` 由请求内容的 hash 决定，同一请求可安全重试并复用已部署文件，不覆盖旧数据。Linux 部署完成后，Windows 应用配置才作为完整文件原子发布。若 Windows 发布失败，Linux 可能保留已部署文件供重试复用；不会自行回滚删除。已有旧脚本或数据不自动替换、迁移，安装桌面更新也不表示会替换正在使用的旧管理器。

### 手动配置（高级／旧环境兼容）

以下示例保留给已有兼容管理器的高级或旧环境，不是全新用户的必需步骤。路径为旧环境示例，需按实际发行版、用户和家目录调整。手工填写 Windows JSON 只指定控制入口，**不会生成其指向的脚本或 Linux 配置**；需确认这些文件已存在。修改后点击“重新检测”，Windows 与 WSL 配置端口必须一致。

~~~json
{
  "Distribution": "Ubuntu-26.04",
  "LinuxUser": "yangzhe",
  "LinuxLauncher": "/home/yangzhe/.local/share/dsh-windows-launcher/launcher.py",
  "LinuxConfig": "/home/yangzhe/.local/share/dsh-windows-launcher/config.json",
  "StartupTimeoutSeconds": 120,
  "ProbeTimeoutSeconds": 15,
  "StopTimeoutSeconds": 45,
  "Port": 3080,
  "WindowWidth": 1200,
  "WindowHeight": 800
}
~~~

### Windows 配置与 Linux 服务配置的区别

- Windows 配置的 `Distribution`、`LinuxUser` 指定 WSL 发行版和用户；`LinuxLauncher` 指向已有 Python 管理脚本，`LinuxConfig` 指向它读取的 Linux JSON 配置。发行版名称可在 Windows PowerShell 中用 `wsl --list --verbose` 确认。
- Linux 服务配置至少包含以下字段；示例路径均需替换，Node 应是 WSL 中真实存在、符合 Harness 版本要求的可执行文件。可在所选 WSL 用户的终端用 `node -p 'process.execPath'` 查看当前 Node 绝对路径。

~~~json
{
  "repository": "/home/your-user/deepseek-harness",
  "node": "/home/your-user/.nvm/versions/node/v24.22.0/bin/node",
  "state_directory": "/home/your-user/.local/state/dsh-windows-launcher",
  "port": 3080
}
~~~

`repository` 是 Harness 源码根目录，`state_directory` 是 Python 管理器的状态/日志目录，不是业务项目目录，也不等于 `DSH_HOME`。原管理器若使用 `home`（对应 `DSH_HOME`）等额外字段，应按其约定保留。设置界面只改 `repository`，不会替换 Node 或迁移已有会话数据。

首次引导使用随包内置管理器，不要求自行取得旧脚本。上述手动 JSON 仅用于兼容已有管理器（支持 `probe` / `run` / `stop` / `logs` 协议），不是管理器程序本身；不会自动替换这些旧路径对应的脚本或迁移数据。

更新 nvm/Node 后，若原绝对路径失效，需要更新 WSL 管理配置；应用不依赖交互 shell 初始化。

## 启动环境检查

启动时自动检查 WSL、启动配置、发行版、Linux 用户、Python、管理脚本、WSL 服务配置、DSH 项目目录、Node.js、已安装依赖与 Web 产物。全部通过后检查/启动服务并自动打开 DSH，无需点击继续。

首次引导与已有配置的启动检查是两条入口：首次引导先收集必要配置，并在明确确认后部署；配置就绪后的初始化画面展示“检查运行环境 → 准备本地服务 → 打开 DSH”三个阶段，不混放通知、更新及服务控制。详细检查列表默认收起；失败时直接显示异常原因和处理提示，提供“重新检测”和“打开设置”。依赖上游的项目显示“等待前置项”，不连锁全部报错。只检测，不自动安装、克隆或执行构建；重新检测会读取最新配置，无需重开应用。

点击左上角 Logo 旁独立的“设置”齿轮图标，在当前窗口的设置页中选择“环境与目录”，通过 Windows 原生 `IFileOpenDialog` 系统弹窗选择 **WSL 内的 DSH 根目录**，只读字段显示转换后的 WSL 绝对路径；不手输，拒绝 Windows host 或其他发行版。点击“保存并重新检测”验证项目入口，只更新已有 Linux 服务配置的 repository 字段，保留其他字段与文件权限；通过后自动进入 DSH。这属于已有配置的目录更新，不会重新执行首次部署；缺少原管理脚本或 Linux 配置时需手动修复。运行时须先通过托盘右键菜单停止服务才能改目录，不会自动停止或重启已有服务。

## 桌宠气泡通知

鲸鱼娘默认开启气泡通知，复用现有只读任务检测：本轮结束、失败或需要回答/确认时，在桌宠旁显示任务摘要。点击气泡进入原 DSH 会话，关闭按钮或约 12 秒后收起；悬停、聚焦或打开右键菜单时暂停计时。气泡出现时暂停随机漫游。通知与交互气泡按角色锚点、实际内容尺寸和可见区域自动计算位置；贴边时避让，空间不足时限制在现有 360×320 窗口内，通知尖角随方向调整。拖动、缩放、内容变化和交互卡片展开/收起后重新布局，不为气泡扩大窗口。

自动提醒的卡片互斥：**桌宠显示时不弹 Windows 通知卡片，但系统通知开启时仍播放通知语音；关闭气泡不关闭通知语音。桌宠隐藏时按系统通知开关显示卡片并播放对应状态语音，卡片自身静音，不额外双播，不补发历史气泡。** 通知语音使用预生成并嵌入程序的 PCM WAV：完成“任务完成啦”（V2 原音裁剪，1.70 秒）、失败“糟糕，任务好像失败了。”（2.32 秒）、待确认“任务需要确认一下”（2.32 秒）。运行时通知不调用千问、不加载模型，也不需要安装语音组件，与长回复朗读独立；无需外部音频文件。通知语音由系统通知开关控制，沿用 Windows 系统声音会话的音量与静音，不再读取系统声音方案。勿扰模式或 Windows 通知设置可能屏蔽横幅，通知语音由应用单独播放，不保证随横幅一起被抑制。前台静默，是否前台也提醒沿用“系统通知 → 窗口聚焦时也通知”，该选项可在系统通知关闭时单独配置。手动“测试通知”仍用于测试 Windows 渠道，播放完成语音“任务完成啦”。

气泡只显示会话名称和固定任务摘要，不显示聊天正文；通知点击目标仅在 Rust 中暂存，前端只能提交短期不透明 ID，不能传 URL、路径或任意会话跳转参数。

### 在气泡中回答与确认

桌宠显示且气泡开启时，待处理问题、计划评审和权限请求可直接在气泡中操作：单选、多选、输入回答、提交整批答案；计划可明确批准或选择继续规划并附反馈；权限只提供**允许一次／拒绝**，不提供永久授权。

待处理交互不会按 12 秒自动消失，也不受普通任务提醒的前台静默控制；关闭按钮只收起，不同意、不拒绝、不取消。原 DSH 可同时处理，已处理/取消/过期的旧按钮会失效。授权正文展示完整原因、参数及必要的根程序/父调用链；拿不到完整信息就禁用“允许”，仍可拒绝或在 DSH 处理。断线结果不明时只读重连，不自动重发授权。

回答或授权会继续原任务，可能产生原 DSH 的正常模型和工具费用，不创建新会话或额外提示词。普通完成/失败气泡仍按前述规则显示。

## 系统通知

点击左上角 Logo 旁独立的“设置”齿轮图标，在当前窗口的设置页中选择“系统通知”，开启“任务通知”，点击“发送测试通知”。设置独立保存在 `%APPDATA%\io.local.dsh-wsl-desktop\notifications.json`，不会回写旧启动器或 DSH 配置。

- 默认仅在 DSH 工作窗口不处于前台时提醒；开启“窗口聚焦时也通知”后，即使工作窗口已打开并处于聚焦状态，也会提醒。该选项默认关闭并独立保存，关闭再开启任务通知会保留此偏好。关窗隐藏到托盘后仍检查，退出启动器后停止。
- 后台约每 3 秒通过已登录工作 WebView 的同源认证状态调用本机只读会话接口；不启动额外服务、不接管权限确认或用户提问，不给 DSH 页面开放原生 IPC。
- 正常结束、失败，以及等待用户选择、回答问题或确认计划时会提醒；支持 `run_code` 内嵌套调用。取消、输出截断、恢复的历史结束标记及子代理不报成功。通知按完成、失败、待确认状态播放上述内置预生成语音（手动测试通知播放完成语音），并显示对应会话名称；标题缺失或无效时显示“未命名会话 · 短编号”。名称压缩为单行，过长时截断；结束、失败和待答提醒均包含名称。不额外提取问题／回答正文、错误详情、项目路径或凭据。会话名称可能由首条提问生成，Windows 通知中心可能保留名称，请勿在名称中放入敏感信息。“本轮结束”不等于整个长任务目标完成。
- 阻塞问答根据运行中的工具调用及其结束事件判断，连续两次检查仍待处理才提醒，通常约 3–6 秒，过滤很快失败或已回答的调用；这是一种只读状态推断，不是问答弹窗的精确事件订阅。定时问答继续沿用待答投影，并过滤已排队的回答。同一个问题只提醒一次，回答或取消后不再提醒，不会代替用户作答。
- 执行结果在首次连接、重连或重新启用时只建立基线，不补发历史结果；仍待回答的问题会被检查。同一启用周期内网络重连不会重复提醒已消费的问题；重新启用可提醒当前仍待答的问题。同一会话一次检查间隔内多轮执行合并为最近一轮结果，前台已消费的提醒不会在切后台后补发；切换“窗口聚焦时也通知”不重置记录，也不补发已消费的提醒。
- 点击任务通知会唤起原有 DSH 工作窗口并切到对应会话；在设置页或隐藏到托盘时也会恢复工作区，不重启服务。需要配套支持 `#session=<编码后的会话 ID>&notification=<编号>` 的 Harness 前端；仅更新启动器不能让旧版 Harness 自动具备跳转能力。会话已删除或不可用时不创建新会话。测试通知不绑定会话。仅支持启动器仍在运行时点击，不注册协议或在退出后自动拉起；最多保留 128 条可点击任务通知，超出时尝试移除最旧一条；正常退出时尝试清理本进程的任务通知，系统调用失败时旧条目仍可能保留。
- Windows 系统通知需用 **安装后的应用** 验证。调用成功只表示提交给系统，不保证横幅出现；请检查“设置 → 系统 → 通知”以及勿扰模式。测试通知不要求 Harness 已连接。

验收建议：开启后等待状态显示“正在检查”，后台执行正常／失败任务，以及普通问答、`run_code` 内嵌套问答和计划确认；检查待答提醒有音效且不重复、回答后停止提醒、默认前台静默、打开聚焦通知选项后前台也提醒、切换选项不重复通知、取消不报成功、关闭后不提醒、重连不补历史结果、重启后保留开关。WSL/Linux 单测和交叉编译不能替代 Windows 通知横幅实测。

## GitHub Actions 构建（推荐）

[Windows build 工作流](<.github/workflows/windows-build.yml>)仅在推送 `v*` 版本标签时运行。普通分支推送、PR 和手动触发均不启动工作流；日常开发请在本地运行测试。

1. Ubuntu runner 验证前端、Rust 和 fake-service Python 测试。
2. 测试通过后，Windows Server 2022 runner 使用 MSVC 编译，执行 Windows 单元测试并生成 x64 NSIS 安装包。
3. 测试和 Windows 打包成功后，验证更新签名并自动创建 GitHub Release，上传完整下载附件后公开。

标签构建包含独立可执行文件、NSIS 安装包、更新签名、版本清单和 SHA256SUMS.txt。Actions Artifacts 保留 30 天，下载通常需要登录 GitHub；正式版本请从 [Releases 页面](https://github.com/elves-ai/dsh-wsl-desktop/releases)下载，公开 Release 附件不受这 30 天保留期限制。

默认 GitHub Token 为 contents:read，仅标签发布 job 获得 contents:write。标签构建需要更新签名私钥 Secret，缺少私钥时直接失败，不回退为无签名发布；配置见[更新说明](<UPDATES.md#发布维护者首次配置>)。第三方 Actions 固定到提交 SHA。

### 发布新版本

版本标签必须匹配四份元数据：[package.json](<package.json>)、[package-lock.json](<package-lock.json>)、[Cargo.toml](<src-tauri/Cargo.toml>)、[tauri.conf.json](<src-tauri/tauri.conf.json>)。支持 vX.Y.Z 和 vX.Y.Z-预发布标识；版本不一致会在构建前失败。修改版本并提交后，例如：

~~~bash
git tag v0.1.3
git push origin v0.1.3
~~~

发布 job 先下载同一次工作流的 Windows 产物，重新验证全部附件校验和、更新签名和版本清单，再创建草稿 Release、上传完整附件、核对附件清单，最后公开 Release。预发布标签会标记为 Pre-release，不取代最新稳定版。失败时可能留下草稿，重跑可继续；已经公开的版本拒绝覆盖，应修复后发布新版本，不移动旧标签。维护者应限制版本标签的推送权限。

**构建未配置代码签名**：Windows SmartScreen 可能警告，请核对来源和 SHA256。构建机不需要你的 WSL 或 DSH 凭据；CI 不启动应用，不会连接或重启你电脑中的服务。

## 本机 Windows 构建（可选）

本节仅供需要自行构建 Windows 启动器的开发者使用；普通用户下载发布包即可，与上面的 Harness 源码构建是两件事。Windows 端需要 Node.js 24/npm、Rust stable MSVC 工具链、Visual Studio C++ Build Tools、Windows SDK 和 WebView2 Runtime。

[构建脚本](<scripts/Build-Windows.ps1>)只检查工具，不自动安装或更改系统配置。它把源码暂存到 Windows 本地目录，避免 npm/cmd 的 WSL UNC 工作目录问题；不会复制 Linux 依赖和隔离工具。

在 Windows PowerShell 执行：

~~~powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "\\wsl.localhost\Ubuntu-26.04\home\yangzhe\work\dsh-wsl-desktop\scripts\Build-Windows.ps1"
~~~

成功后可执行文件和 NSIS 安装包写入项目的 artifacts/windows/ 目录。脚本不执行安装包、不启动应用、不替换旧快捷方式。Windows 构建缓存位于 %LOCALAPPDATA%\DSHWslDesktopBuild。

如果源码本来在 Windows 本地目录，也可以执行：

~~~powershell
npm ci
npm run desktop:dev
npm run desktop:build -- --config src-tauri/tauri.local-build.conf.json
~~~

不要在 WSL 中执行普通 tauri build 并期待 Windows 应用。本项目不提供 Linux GUI；Linux 仅用于编辑、纯逻辑测试和交叉编译检查。

### Windows 首次引导验收（待实机执行）

以下是验收清单，不是已通过的 Windows 实测报告；本次文档更新未运行应用或真实服务。使用隔离的 Windows 用户／测试 WSL 环境，不删除或替换个人现有配置和数据。

- **入口分流**：新旧 Windows 配置均不存在时显示引导；仅有有效旧配置时照旧导入且源文件不变；已有新配置时使用新配置；无效新配置或无效旧配置均应报错，不自动覆盖。

### 验证边界

已完成前端生产构建、Rust 单测、Python 停止归属测试与 Windows 目标源码编译检查。已确认原服务 WSL ready、Windows 同地址返回预期的 401。原服务没有被停止/重启，旧快捷方式没有被替换。

Windows 安装包由 GitHub Actions 的 Windows runner 生成，以对应运行的成功状态和实际上传产物为准。本机交叉 cargo check 不代表链接、打包成功；CI 的编译/打包成功也不代表真实 WSL + WebView 已完成端到端验证。

Windows 验收还需覆盖：首次认证及重开登录状态、流式响应、关窗后台运行、托盘恢复、单实例、文件上传/下载、外链与预览、多显示器/DPI，以及确认取消/停止失败/拒绝外部实例等流程。自定义标题栏另需实测设置齿轮的鼠标与键盘操作、Logo 不响应点击且无下拉菜单、边缘缩放、拖动、双击最大化 / 还原、最小化、关闭隐藏到托盘，以及缩放比例变化后标题栏不遮挡内容；浏览器预览和 Windows 目标源码检查不能替代这些原生验收。

任务防休眠的 Windows 原生验收：开启设置并运行任务，用只读的 `powercfg /requests` 确认启动器持有 SYSTEM 请求；确认屏幕仍能正常熄灭。再覆盖多会话仅结束其中一个、子代理独立运行、隐藏到托盘、全部完成/失败/取消、关闭开关、退出但保留服务、断线超过 30 秒及重新连接。空闲、关闭或退出后不应残留本启动器的防休眠请求。纯逻辑单测与 Windows 目标源码检查不能替代真实 Windows 休眠行为验证。
