# Privacy policy

Last updated: 2026-10-24

## Scope

This policy describes the DSH WSL Desktop launcher maintained by Evan Yang, an individual. It is not a privacy policy for DeepSeek Harness (DSH), its model providers, extensions, third-party legacy WSL helpers, Microsoft WebView2, or websites opened in the system browser.

The launcher does not implement its own analytics uploader, account service, or maintainer-operated data-collection endpoint. This does **not** mean that the embedded DSH application, its tools, WebView2, or external services are prevented from communicating with other systems.

## Local configuration and service control

The application uses existing Windows launcher settings or imports legacy Windows settings without changing the original. First-run setup appears only when neither configuration exists; invalid existing configurations are not automatically overwritten. Setup collects the WSL distribution and Linux user, Harness source root, and an existing Node executable (detected from the highest installed nvm version or system Node, or manually specified), with default port 3080 and an advanced override. Settings also include helper/configuration paths, timeouts, and window size. They stay in local configuration storage and are not uploaded to the maintainer.

The application invokes the configured helper through Windows Subsystem for Linux to check, start, or explicitly stop DSH. It also makes HTTP readiness requests to the configured loopback address, normally http://127.0.0.1:3080/. Starting the desktop app may start the existing DSH service. Stopping or restarting requires a native confirmation and may interrupt existing tasks.

The helper and DSH can access local projects, credentials, conversations, model providers, and other tools according to their own configuration and permissions. Review their settings and upstream documentation before use. This launcher does not audit, replace, or disable those systems' data handling or telemetry.

Startup environment checks read WSL availability, the configured Linux files and project metadata, and run bounded Node version/module-resolution probes without importing project code. They do not install software, clone repositories, or build the project. For first-run setup, only clicking “完成配置并启动” (Complete setup and start) authorizes deployment and generation of both configurations, after the same read-only environment checks pass. The launcher embeds its own MIT-licensed Python manager 1.0.0 using Rust `include_str!`; that version is paired with the desktop package, with no remote “latest manager” download. It requires an existing WSL installation, `/usr/bin/python3` (>= 3.9), `ss`, Node, installed Harness dependencies, and a completed Harness build; it does not configure API keys. With an existing configuration, explicitly saving a DSH directory updates only the repository field in the existing Linux helper configuration; other fields and permissions are preserved. Legacy scripts and data are not automatically replaced or migrated. Detection results and the configured project path are shown locally and are not uploaded to the maintainer.

## Embedded browser and external services

The working window loads the locally running DSH website using WebView2. A launch authentication URL can be passed to that local service, and browser data such as cookies, cached content, or local storage may persist in the WebView profile. Authentication URLs and browser-profile files should be treated as sensitive.

Top-level navigation and popup restrictions are not a network sandbox for page subresources, fetch requests, WebSocket connections, or engine/system services. DSH features may communicate with remote model providers or other configured services. Review the policies of those providers; do not assume conversations remain local merely because the desktop page is served from a loopback address.

Permitted external web links are opened using the system's default handler. Data processing at the destination is governed by that site's and browser's policies. The installer may download/install Microsoft WebView2 Runtime when it is required. Microsoft's [privacy statement](https://privacy.microsoft.com/privacystatement) applies to Microsoft services and components.

## Optional desktop notifications

Desktop notifications are off by default. If enabled, the native launcher reads only the HttpOnly authentication cookie bound to the configured loopback service authority from the DSH working WebView and uses it in memory for read-only session-list and recent-history requests, approximately every three seconds. These requests bypass proxies and do not follow redirects. No launch token is reused and no authentication data is exposed to the local control page, notification text, or launcher logs.

The session API may return conversation data in the inspected history page. The launcher classifies the latest turn-ending reason and sequence, and checks running tool starts/results and pending-question projections for a request to choose, answer, or review a plan. Its cursor/deduplication state retains only opaque session/call identifiers, not question arguments or conversation text. For each reminder it also reads the matching session's title string from the session-list title projection, normalizes it to one line, and truncates long names; a missing or invalid title falls back to an unnamed-session label with a short session ID. It does not use conversation bodies, question arguments, error payloads, workspace paths, or authentication fields to build notification text, and does not persist API responses or copy task names to launcher snapshots or activity logs. DSH may generate a session title from the first user message, so the title itself can contain a conversation excerpt or sensitive text. Windows may retain the displayed title and notification in its notification center according to system settings; avoid sensitive information in session titles. Disabling notifications stops new checks and submissions, but does not remove notifications already submitted to Windows. Quitting the launcher stops notification monitoring without stopping DSH. Task notifications retain a native Windows handle and an in-memory callback containing an opaque session ID and the original loopback service target. Clicking one restores the existing workspace using an encoded URL fragment; the fragment may appear in WebView/browser navigation history, but is not sent in an HTTP request or recorded in launcher logs. No arbitrary activation URL is accepted, no script is injected into DSH, and no service is started or restarted on click. The matching frontend must support this fragment navigation. Activation is only supported while the launcher is running, including in the tray; no OS protocol/cold-start registration is made. At most 128 task notifications are retained. The oldest is removed on overflow; dismissing or activating a notification releases its handle, while banner timeout retains it for Notification Center. Normal exit attempts to remove this process's remaining task notifications. Generic test notifications are not session-bound.

Only the non-secret enabled preference is stored in a separate local notifications.json file. Initial connections and reconnections establish a fresh baseline rather than replaying old completed results. Still-pending questions can produce a reminder; deduplication across network reconnections prevents repeating an already-consumed reminder within the current enabled period. The read-only inference never answers a question, submits a plan decision, or joins the interaction-answerer stream.

## Optional desktop assistant

The tray entry “桌面助手…” opens a bundled local pet and conversation panel. Only confirming “确认并启用” authorizes preparing the chosen independent WSL directory (default `~/DSH-Assistant`), registering/reusing a DSH Workspace and creating a Session. Project/session records stay in the configured DSH storage, not in a separate desktop transcript database. Sending text can invoke the model and tools configured in DSH and incur their normal costs.

Unlike the read-only notification worker, the assistant is a conversation client: native Rust code holds the matching DSH authentication cookie in memory, sends fixed-purpose Workspace/Session RPCs over local HTTP, and reads history and live output through a dedicated local WebSocket subscription. The conversation-follow subscription does not join the question/approval event stream. Following a saved assistant Session may resume its Agent. Separately, visible enabled pet bubbles can register the existing owner browser credential for real interactive requests, as described below. The conversation panel receives conversation text, session titles, and generic tool state, but not authentication cookies, hidden reasoning, raw tool arguments or tool output; interactive approval bubbles are the explicit exception for the complete operation parameters the user must review. There is no assistant-specific maintainer endpoint or automatic prompt retry. Disabling Windows notifications does not stop the assistant.

The application saves backend identity, WSL workspace path, Workspace ID, selected Session ID and pending-creation state in `assistant-binding.json`, and the pet position in `assistant-position.json`, under the application configuration directory. These contain no transcript or API key. Unsent drafts are kept per conversation in the panel’s WebView sessionStorage and may be retained by WebView2. Messages and streamed text also exist in process memory while the panel runs; browser engine storage has its own behavior. Hiding a surface does not delete these records or stop DSH work. Rebinding does not delete the old Workspace, Session or directory. Uninstalling the Windows app does not delete DSH conversation history or the chosen WSL directory.

The desktop pet reuses packaged local animations and pure selection/physics code from PC2005-cloud’s dsh-pet: <https://github.com/PC2005-cloud/dsh-pet>. Code is MIT; animation assets prohibit commercial use and require original-author attribution on derivative displays/distributions. Animation playback does not fetch upstream servers or import the upstream Electron host, prompt generator, model settings or balance services. Only explicitly clicking the source link opens GitHub in the system browser. During pet dragging/motion and hit testing, native code reads current pointer coordinates, left-button state and monitor work areas to move the pet; coordinates are temporary in-memory samples, not a recorded input history or uploaded telemetry. The last pet window position is persisted locally.

The titlebar pet icon only toggles the current pet window and receives a minimal visible/revision projection, never chat history. The “桌面宠物” settings page can change current visibility and persist exactly three booleans (show at application startup, allow random roaming, enable pet notification bubbles) in pet-settings.json under the application configuration directory. Current visibility does not overwrite startup preference. Startup display defaults off and random roaming defaults on. Hiding does not cancel DSH work; these controls do not create a project, send a prompt or start/stop the WSL service. Preferences are not uploaded; malformed files are reported and not silently overwritten.

Passive pet bubbles reuse read-only task/result/attention detection without generating an extra prompt. Interactive bubbles separately subscribe to the authenticated owner’s global `$events` stream and submit explicit structured answers through `$events/result`; they do not acquire unique ownership or replace the DSH UI. Automatic delivery is exclusive: while the pet is visible, only enabled bubbles are delivered (disabled bubbles mean silence); while hidden, Windows notifications follow their own enable flag. The shared foreground opt-in remains explicit. Summaries include session names and fixed status text, not chat bodies. The native pet inbox holds at most 32 opaque click targets for five minutes in memory, never on disk; the UI sees only ID/kind/title/body. Hidden/disabled pets discard queued bubbles, and dismissed notifications are acknowledged. Clicks accept only an opaque ID and reuse the existing current-origin session navigation checks.

Interactive requests carry original question text, complete plans, approval reasons and verified complete tool arguments (including parent/root program parameters for nested calls). This material and input drafts are held in process/WebView memory, not a separate transcript file or launcher log. No authentication cookie or Host client/event correlation is exposed to the pet. Native Rust maps opaque IDs to at most 32 current requests and rechecks origin, cookie, visibility and current membership before an explicit answer. Authorization is once-only or rejection; missing complete details disable allow. Clicking X or hiding the pet does not answer/cancel and retains live wait claims. Disabling the feature or disconnecting withdraws this client without sending a business rejection. Other UIs may settle the same request; cancellation removes stale buttons. Uncertain delivery triggers read-only reconciliation, never automatic resubmission. These persistent interactions are distinct from 12-second passive notifications and are not hidden by the passive foreground-quiet option. Submitting may resume the original task and its normal model/tool costs.

## Optional local Qwen narration

Manual narration and the separately enabled automatic read-aloud feature send cleaned assistant-reply prose through PET-only native IPC to a fixed local helper at http://127.0.0.1:18765. The request contains only a unique speech-request identifier and a bounded text segment, not DSH authentication cookies or session credentials. Cleaning skips code blocks and URLs but is not a sensitive-data classifier: ordinary prose can still contain private information. Native speech HTTP requests bypass proxies and do not follow redirects.

Qwen automatic narration defaults off and does not inherit the old system-voice opt-in. Its non-secret automatic-read and volume preferences share the native speech settings store with the trusted settings view. The old separate `dsh-assistant:qwen-auto-read` key is read only for one-time migration before native preferences have been initialized; an explicit newer native choice is never overwritten. Enabling affects future completed replies, not history or reconnect hydration. Explicit playback or opt-in clicks may be needed to unlock browser audio. Audio generation and decoding use process memory; stopping discards late results and does not delete DSH conversation history.

The helper runs in WSL with externally configured Q8 GGUF model files and a trusted external native library (C ABI 6) plus its adjacent ggml libraries and ROCm SDK dependencies. Python is the local security/process bridge; ctypes loads the native library only in an isolated spawn child for ROCm GPU inference. A native library is executable code, not an inert model file; use only trusted builds. The complete packaged, user-selected 8.4-second synthetic reference clip and transcript are used together for ICL, not embedding-only conditioning. No PyTorch/MIOpen inference or CPU, CUDA, Windows-native Python, or system-voice production fallback is used. The helper has no automatic model downloader, remote speech provider, or transcript/audio-file logger. Input segments, generated WAV bytes, reference conditioning and runtime tensors can exist in process and GPU memory while it runs; this is not a secure-memory-erasure guarantee or an operating-system network sandbox. The model child can remain resident until its helper exits through a managed stop/app exit or manual termination; cooperative native cancellation is used where available, with child termination for stages that cannot stop within the grace period. Installing dependencies, obtaining native source/builds, and downloading the two model files are separate explicit operations that can contact package/code/model hosts under their own policies. The desktop app does not bundle model weights, automatically install WSL/Python/ROCm, download weights, or build a native library. Trusted settings can validate external paths, start/prepare/audition an owned WSL helper, and stop it to release GPU memory. Only small bridge sources and the approved reference are staged into a private WSL cache. Managed credentials travel through private stdin and authenticated loopback headers, not argv, public status, UI snapshots or diagnostics. An owned held-stdin lifecycle and checked supervisor identity stop only this application’s process group on exit or owner-channel loss. External manually started services are not taken over or stopped. Refresh is lightweight, never an implicit model load or synthesis. Path changes cannot replace a live service’s configuration silently. External runtime, source/build and model directories are user-managed and remain after uninstalling the desktop app. See [local narration setup](<QWEN_SPEECH.md>).

## Task-scoped power management

Sleep prevention is enabled by default and can be disabled under Settings → 电源管理 (Power management). Independently of notifications, this worker uses the same authority-bound HttpOnly cookie and bounded, proxy-free, non-redirecting local RPC transport to read only session/list approximately every three seconds after service readiness. It uses live running flags, including subagents, to control a temporary Windows system sleep request. It does not request conversation-history pages, expose credentials to the settings page, or persist session-list responses. Only the enabled preference is saved in a separate local power.json file; generic status transitions and errors can appear in the launcher activity log.

Hiding the workspace to the tray does not stop monitoring. Disabling notifications stops notification checks only, not this independent power worker. Disabling power management stops its session checks and releases the request; quitting the launcher ends both workers even if WSL keeps running. Temporary query errors keep an existing request only for a bounded grace period of approximately 30 seconds after the last valid running observation. No system power plan is changed.

## Update checks and downloads

Updater-enabled versions check this project’s latest stable GitHub Release once at launcher startup and when requested. These requests expose the client IP address and ordinary HTTP/TLS metadata to GitHub and its download infrastructure. The launcher does not attach DSH tokens, conversations, launcher configuration, or activity logs to these requests. It uses system network/proxy settings and Windows TLS trust; an environment-controlled proxy may also observe connection metadata.

After explicit native confirmation, the launcher downloads an NSIS update package from this project’s GitHub Release, verifies its version-bound update signature, and runs the installer. The Windows launcher/workspace closes and restarts, but this operation does not stop or upgrade the WSL service. Installer temporary files may remain in Windows temporary storage, especially after failures; automatic cleanup is not guaranteed. There is no mirror or maintainer-operated update server. See [update behavior](<UPDATES.md>).

## Activity logs

The launcher keeps a recent in-memory activity list and a local activity log for startup stages, service-control actions, and errors. It does not intentionally copy DSH conversations or the configured helper's service log into this activity log. Common token and Bearer forms are redacted, but redaction is not a guarantee that arbitrary user-supplied text is free of sensitive information.

The in-memory list retains up to 120 entries. If the activity-log file is already larger than 512 KiB, the next write truncates it; this is not a strict maximum file size. There is no automatic upload of these launcher activity logs. Review logs before sharing them in support requests.

## Storage and removal

Typical Windows locations are:

~~~text
%APPDATA%\io.local.dsh-wsl-desktop\config.json
%APPDATA%\io.local.dsh-wsl-desktop\notifications.json
%APPDATA%\io.local.dsh-wsl-desktop\launcher.log
%LOCALAPPDATA%\io.local.dsh-wsl-desktop\webview
~~~

The working WebView uses the last directory. WebView2 and the local control window may also use engine/system storage. Existing DSH and legacy helper data remain in their separately configured locations.

First-run setup additionally deploys these files/directories under the selected Linux user:

~~~text
~/.local/share/dsh-wsl-desktop/manager-1.0.0.py
~/.local/share/dsh-wsl-desktop/profiles/<profile-id>/config.json
~/.local/state/dsh-wsl-desktop/<profile-id>
~~~

The final directory holds manager state/logs, not DSH_HOME. A hash of the setup request contents determines `profile-id`; identical retries can reuse deployed files without overwriting old data. The complete Windows configuration is atomically published last, after Linux deployment. If Windows publication fails, deployed Linux files may remain for reuse on retry; the launcher does not automatically roll back by deleting them. These Linux files may also remain after uninstalling the Windows application.

Closing a window hides it; quitting the launcher does not by itself delete configuration, activity logs, browser data, or DSH projects. The launcher has no built-in clear-all-data control. An installed copy can be uninstalled using Windows Installed apps. Automatic data cleanup during uninstallation has not been verified; inspect remaining application directories before removing them yourself. Do not delete DSH projects or authentication data unless you intend to remove them.
